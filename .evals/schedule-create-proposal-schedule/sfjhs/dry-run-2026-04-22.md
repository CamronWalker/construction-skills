# SFJHS Dry-Run — Updated Skill vs RFP

**Purpose:** Validate the updated `schedule-create-proposal-schedule` skill would now catch the failure modes the v14 XER exhibited. This is a mental walk-through of Phase 2 + Phase 3 against the actual SFJHS RFP (NSDRP26-0401). Not a re-run of the full skill — just the decision points the SFJHS Lessons Learned flagged as missing.

**RFP source of truth:** Direct read of `Bid Documents/1 Nebo School District RFP CMGC SFJHS Rebuild NSDRP26-0401 (2).pdf`, Section 2.1, 2.7, 3.2.8, 3.3.5.

## Phase 2 — What the updated skill would extract

### Delivery Method
**CM/GC.** Stated in RFP title, Section 1, Section 2.1.
→ **Triggers:** Design schedule activities belong in the schedule (Phase 3 "Design schedule" bullet fires).

### Phasing & Occupancy Profile

| Field | RFP says | Source |
|---|---|---|
| Occupancy during construction | **Full occupancy** of existing school | §2.1: *"The existing school will remain operational throughout construction..."* |
| Demolition timing | **After SC** of new school | §3.2.8: Demo NTP 6/1/28; new school SC 6/30/28 → demo begins at/after SC |
| Post-demo site use | **Fields / tennis courts / paving** (no additional structure) | §3.2.8: *"ALL SITEWORK INCLUDING LANDSCAPING, TENNIS COURTS, FIELDS, ETC., SHALL BE COMPLETED NO LATER THAN SEPTEMBER 15, 2028"* |
| Turnover phases | Three sequenced completions: new school → demo → sitework | §3.2.8: SC 6/30/28 → Demo SC 7/31/28 → Sitework complete 9/15/28 |

**Result:** The Phasing & Occupancy Profile is unambiguous. Full occupancy + demo-after-SC + old footprint → fields is a textbook Pattern B trigger.

### Contract Milestones extracted

- Subcontractor Bids Due: 11/01/2026

RFP does NOT specify SD/DD/70%/100% CD dates. It says GMP at 85% CD completion.
→ Phase 3 should include design-phase activities with durations flagged "needs design team input" per the updated rule, and list the 85% CD milestone as the GMP trigger.

## Phase 3 — What the updated skill would propose

### WBS pattern choice (the headline check)

With the Phasing & Occupancy Profile above, `wbs-patterns.md` decision table maps directly:

| Occupancy during construction | Demo timing relative to SC | Pattern |
|---|---|---|
| ✅ Full occupancy of the existing structure | ✅ At or after Substantial Completion | **B** |

**Prompt the skill would produce** (per Phase 3 updated text):

> *"Based on the phasing profile (full occupancy through SC, demo after SC on 6/1/28, old footprint becomes fields/tennis/paving by 9/15/28), I'm using **Pattern B**: DEMOLITION top-level **after** CONSTRUCTION, with FINAL SITEWORK nested under DEMOLITION for the post-demo footprint work (landscaping, tennis, paving, striping, mow strips, topsoil, irrigation, playground, bollards, hardscape, site lighting). Confirm before I lay out activities?"*

**✅ PASS.** This is exactly the WBS structure the human scheduler used and the v14 missed. The updated skill would not jam the 14 post-demo activities (SFJHS4890–SFJHS4970) into `CONSTRUCTION/SITEWORK/SITEWORK COMPLETION` — they'd go under `DEMOLITION/FINAL SITEWORK/{INITIAL|BALANCE|COMPLETION}`.

### Task code prefix

> *"Rename task codes from sample prefix (PCSD- / PES-) to project prefix (SFJHS-), or keep sample codes for traceability?"*

**✅ PASS.** Asked, not assumed. The v14 silently bulk-renamed 400 activities.

### Design schedule handling (CM/GC)

Updated rule fires because delivery method = CM/GC. Phase 3 output includes SD, DD, 70% CD, 100% CD, Permit/Consent as activities in PRE-CONSTRUCTION/DESIGN with durations flagged "needs design team input" (RFP §2.1 confirms a concurrent SD was completed 4/1/2026 — everything downstream of that is open).

GMP milestone wired to 85% CD completion per RFP §2.7.

**✅ PASS.** The v14 had GMP as a fixed date without the 85% CD anchor.

### Procurement pairs + installation ties

New rule: every long-lead gets fabrication + shipping activities, tied to its installation activity.

Long-leads extractable from the RFP scope and PES sample (typical temple/school commercial): structural steel, MEP equipment, elevators, custom entry doors, decorative lighting, etc. Each becomes a fabricate → ship → install chain.

**Guard rail fires** if any procurement chain solo-drives the first N months of the schedule. SFJHS window: 11/1/26 NTP → 6/30/28 SC = ~20 months. A 12-month procurement should be roughly months 3–15 with early-release site packages, design, trade prequal running in parallel months 0–6, mobilization and initial sitework months 3–9, structure months 6–15 — procurement is *one* stream of several.

**✅ PASS on structure.** Real verification needs the XER rebuild, which is out of scope for a dry-run.

### Site Logistics & Workflow Plan

Updated rule: flag as Phase 4 question if none exists. SFJHS project folder has no site logistics plan artifact. The updated skill would surface: *"Has a graphic Site Logistics & Workflow Plan been developed showing zones, crew flow, and phasing for new school construction and post-SC demo? If not, that's the next step before the detailed schedule."*

**✅ PASS.** The v14 silently assumed AREA 1 / AREA 2 zones from the PES sample without validating against the actual site.

## Phase 7 — What would have happened on the v12 → v14 path

v12 hit 90.5 (A-). The updated rule:

> *"Letter grade targets are ranges, not floors. If the user asks for 'at least an A', treat 90 (A-) as the stopping point..."*

**At v12 → 90.5, the skill would STOP and confirm:**

> *"Hit 90.5 (A-). You asked for at least an A — A- is the lower bound of that letter. I can get you higher (~93 A-proper) but only by adding ~100+ soft constraints (CS_FNLT pinning late dates), which a reviewer will read as proposal-stage metric gaming. Cleaner to stop here and produce a narrative note on remaining deductions. Which do you want?"*

**✅ PASS.** v13 (+CS_FNLT rewire on awning chain, 91.5) and v14 (+FNLT=EF+30 BD buffer across 142 long-leads, 95.0) would both require explicit user consent under the new rule. The user saying *"iterate until it's at least an A. B- is not acceptible"* maps to A- = 90 as the stop point under the updated interpretation.

### Open-end classification on the 32 dangling activities

Updated rule classifies before closing. The 32 SFJHS dangles break down:

- **Procurement tails** (e.g., SFJHS1290 Natural Gas Main, long-lead material chains): tie to **installation activity**, not to a terminal milestone. Guard rail: confirm procurement isn't the sole driver of any phase.
- **Intermediate bugs** (true logic gaps): close with correct successor.
- **Terminal activities** (Final Site Survey, Construction Clean, etc.): confirm they genuinely end the project before tying to SC.

The v11 blanket-close-32-with-FS+0-to-Site-Work-Complete would not happen. A classification table would be produced and the user would confirm before mass-closing.

**✅ PASS.**

## Where the dry-run is NOT a full test

These can only be verified by re-running the skill end-to-end and producing a new XER:

- Whether Phase 3 actually composes Pattern B into a correct activity list (LLM-side, not rule-side)
- Whether procurement chains wire to the right installation activities in practice
- Whether the narrative-note fallback produces something the PMT will actually use
- Whether the targeted `quality_checks.py <check>` CLI loop feels materially faster than the full-rescore pattern

The right time for those checks is the next real-project run. That run should produce its own `Lessons Learned - <Project>.md` per the new loop documented in repo CLAUDE.md.

---

## Verdict

Every failure mode the SFJHS Lessons Learned flagged is caught by the updated skill's deterministic rules — the WBS pattern choice, the letter-grade lower-bound stop, the open-end classifier, the procurement-to-installation tie with the solo-driver guard rail. The sales-document framing in the intro is the north star that justifies all of them to a reviewer reading the skill for the first time.

Remaining risk is LLM-side: whether Claude actually *follows* the Phase 3 pattern-confirmation prompt rather than generating activities first and asking after. Mitigation is the explicit "Do not generate activities until the pattern is confirmed" rule in Phase 3 — but real-run proof waits for the next project.
