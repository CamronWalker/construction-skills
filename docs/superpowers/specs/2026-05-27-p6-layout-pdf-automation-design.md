# P6 Layout PDF Automation — Design Spec

**Date:** 2026-05-27
**Status:** Drafted via brainstorming, awaiting implementation
**Owner (decision-maker):** Camron Walker
**Target plugin:** `scheduling` (extends the `schedule-update` skill)

## Problem

Westland's weekly schedule update for each active project includes printing a stack of Gantt-style layouts from P6 Professional to PDF, currently via `File → Print → Microsoft Print to PDF` repeated per layout per project. Measured cost: **3–6 hours per week across 6+ projects** — the single biggest time sink in the weekly cycle, doubly painful because every output already exists as data inside P6.

## Goal

Drive the existing print-to-PDF chain automatically via [Primavera Visualizer's command-line interface](https://docs.oracle.com/cd/F37128_01/visualizer_help/en_US/66408.htm), wire the resulting PDFs into the `schedule-update` skill's existing email-draft + Procore-upload distribution pipeline, and degrade gracefully when individual layouts or the whole tool are unavailable.

## Non-goals (this spec)

- **Activity tables, resource profiles, or other non-Gantt outputs.** Camron is handling those via direct XER rendering as a separate effort. They share no code or config with this spec.
- **Building a custom JS Gantt renderer.** Considered and rejected in the brainstorming: the Visualizer pipeline gives pixel-identical-to-P6 output for free, which matters because the prints go to owners. Trading that fidelity for a 40–80 hour build cost wasn't worth it for v1. See _Alternatives considered_ at the end.
- **Cross-platform.** This is Windows-only by construction (Visualizer is Windows-only, Microsoft Print to PDF is Windows-only). No attempt at macOS/Linux fallbacks.

## Approach summary

A new phase in [`scheduling/skills/schedule-update`](../../../scheduling/skills/schedule-update/) sits between SmartPM screenshots and the email-draft step:

```
copy → screenshots → (NEW) print-layouts → draft → procore
```

The phase reads a per-project `layouts.json` registry, drives `Primavera.Visualizer.EXE` to produce one XPS per registered layout, converts each XPS to PDF via the Windows `Microsoft Print to PDF` virtual printer (the same driver the user already prints through manually), and drops the PDFs in the project's dated update folder. The existing email-attachment scan and Procore-upload pass pick them up unchanged.

If `layouts.json` is missing or empty, the phase logs and exits cleanly — downstream is unaffected.

## Components

Five units, each independently testable. Keep them small enough that a colleague reading any one can hold its purpose in their head.

### 1. Layout registry — `{project}/Schedules/layouts.json`

Per-project, lives **next to** the dated update folders rather than inside `project-context.html`.

Reasoning: layout sets evolve more often than the stable per-project context, and HTML CRUD discipline (see [feedback_html_crud_discipline](../../../scheduling/CLAUDE.md#html-crud-goes-through-the-parsegenerate-pair)) forbids direct read/edit of HTML files with embedded base64 logos. A separate JSON is git-diffable, scriptable, and keeps the blast radius small.

Schema (V1):

```jsonc
{
  "schema_version": 1,
  "project_id": "W1179",                  // P6 project ID — must match what Visualizer sees
  "layouts": [
    {
      "name": "3-week look-ahead",        // free-text, used in filenames + log lines
      "plf_path": "G:\\Westland\\Visualizer Layouts\\3-week look-ahead.plf",
      "output_template": "{project_code} - 3-Week Look-Ahead - {report_date}.pdf",
      "page_size": "Tabloid",             // any size the Visualizer .plf supports
      "page_orientation": "Landscape"
    }
    // ... up to ~15 entries per project
  ]
}
```

`output_template` placeholders rendered at runtime: `{project_code}`, `{report_date}` (YYYY-MM-DD), `{layout_name}` (slug form), `{revision}` (auto-incrementing if file exists).

A starter `layouts.json` should be generated by the project-init skill when a new project's schedule folder is created — covered as an addendum in _Future work_.

### 2. Visualizer driver — `scheduling/skills/schedule-update/references/print_layouts.py`

Pure-Python module. No I/O outside the project folder + temp dir + the Visualizer subprocess.

**Public surface:**

```python
def print_layouts(
    project_root: Path,
    dated_folder: Path,
    layouts_json: Path,
    *,
    visualizer_exe: Path | None = None,    # defaults to env or known install paths
    credentials: VisualizerCreds,           # see auth section
    logger: Logger,
) -> PrintLayoutsResult:
    """
    Print each layout in `layouts_json` to PDF in `dated_folder`.
    Returns counts of succeeded/failed/skipped + the per-layout result list.
    Never raises on per-layout failure — only on global failures
    (Visualizer not found, auth rejected, registry malformed).
    """
```

`PrintLayoutsResult` is a small dataclass with `succeeded: list[Path]`, `failed: list[LayoutError]`, `skipped: list[str]`, `elapsed_s: float`.

**Internals:**
- Build a single `actions.xml` with one `<action type="ganttReport">` per layout (batched).
- Shell out to `Primavera.Visualizer.EXE` with `/username /password /alias /actionScript /logfile`.
- Parse the logfile to determine which layouts succeeded.
- For each failure, retry **once** with a 1-entry actions.xml. Second failure → give up on that layout, continue.
- Hand each successful XPS to the converter (component 3).
- Clean up temp XPS files at end. Keep Visualizer logfile in `{dated_folder}/_logs/visualizer-{timestamp}.log` for postmortems.

### 3. XPS → PDF converter — `scheduling/skills/schedule-update/references/xps_to_pdf.py`

Tiny wrapper. Public surface:

```python
def xps_to_pdf(xps_path: Path, pdf_path: Path) -> None:
    """Convert one XPS file to PDF via Microsoft Print to PDF.
    Overwrites pdf_path if it exists. Raises XpsConversionError on failure."""
```

Implementation: shells to PowerShell using the `Microsoft Print to PDF` virtual printer:

```pwsh
Start-Process -FilePath $xpsPath -Verb PrintTo -ArgumentList '"Microsoft Print to PDF"' -Wait
```

with an output-path hack — `Microsoft Print to PDF` doesn't accept a destination on the command line, so the converter sets the default save path via the registry before invocation and restores it after. Implementer should verify this still works on the target Windows build before committing to this approach; if it's flaky, swap to a different XPS→PDF tool (Ghostscript, `Convert-XPSToPDF` PowerShell modules, etc.). The converter's public surface stays the same regardless of internal implementation.

Lives separately from `print_layouts.py` so it's reusable for one-off conversions (e.g., if a colleague hands you an XPS from somewhere).

### 4. Filename rendering — inside `print_layouts.py`

Pure function, no I/O:

```python
def render_filename(template: str, project_code: str, report_date: str,
                    layout_name: str, dated_folder: Path) -> Path:
    """Substitute template placeholders, slugify layout_name, resolve {revision}
    by checking the folder for existing files with the same base name."""
```

Auto-revision logic: if `W1179 - 3-Week Look-Ahead - 2026-05-27.pdf` exists, the next becomes `W1179 - 3-Week Look-Ahead - 2026-05-27 (rev 2).pdf`. Avoids silent overwrites when the phase is re-run mid-week.

### 5. Phase entry point — `scheduling/skills/schedule-update/phases/print_layouts.md`

Markdown file the schedule-update skill loads as a phase step. Describes the steps the model should follow:

1. Read project-context.html (project_code, report_date)
2. Locate `{project}/Schedules/layouts.json`; if absent, log and skip.
3. Call `print_layouts(...)` with credentials from env.
4. Surface the `PrintLayoutsResult` summary to the colleague: count printed, count failed (with names), elapsed time. Failures listed as "fall back to manual print for: X, Y, Z."
5. Continue to next phase regardless of outcome.

Style: keep colleague-facing, no terminal commands (see [feedback_westland_colleague_docs](../../../scheduling/CLAUDE.md)).

## Data flow

End-to-end for one weekly run:

1. **Trigger.** Colleague runs `schedule-update`'s `report` phase after the schedule meeting; SmartPM screenshots succeed; new `print-layouts` phase fires.
2. **Read project context.** Pull `project_code` and `report_date` from `project-context.html`.
3. **Locate registry.** If `{project}/Schedules/layouts.json` is missing or `layouts` is `[]`, log "no Gantt layouts configured" and exit phase cleanly.
4. **Build actions.xml.** One `<action type="ganttReport">` per registry entry. `<projectID>` from project context. `<outputType>` always `ToXPS`. `<outputName>` is a temp-folder path per layout.
5. **Invoke Visualizer.** Subprocess to `Primavera.Visualizer.EXE` with `/username /password /alias /actionScript /logfile`. Capture stdout + logfile. Global failure (Visualizer missing, auth rejected, alias bad) → raise; phase reports and the rest of the pipeline continues.
6. **Parse Visualizer log.** Determine per-layout success/failure. Build `{layout_name: xps_path | error}`.
7. **Retry failed layouts individually.** For each failure, rebuild a 1-entry actions.xml, re-invoke Visualizer. Two failures → give up on that layout.
8. **Convert XPS → PDF.** For each successful XPS, render the output filename, call `xps_to_pdf(xps, pdf)`. On conversion failure, log and continue.
9. **File in dated folder.** PDFs land in `{project}/Schedules/{dated_folder}/`. The existing email-draft attachment scan picks them up automatically (existing logic globs `*.pdf` in the dated folder).
10. **Report to colleague.** `Printed 12/15 layouts in 142s. Failed: <names>. Manual fallback needed for those.`
11. **Cleanup.** Remove temp XPS files. Retain Visualizer log in `_logs/`.

## Error handling

Three failure categories with distinct semantics:

| Category | Examples | Behavior |
|---|---|---|
| **Global** | Visualizer not installed, alias invalid, auth rejected, `layouts.json` malformed JSON | Phase raises a clear error message naming the cause. Pipeline continues (other phases run). Colleague-facing: "Could not run print-layouts phase: <reason>. Falling back to manual print for all layouts this week." |
| **Per-layout** | `.plf` file missing, layout name doesn't match, XPS conversion fails | Logged and counted as `failed`. Phase continues. Other layouts unaffected. |
| **Skipped** | Empty registry, no `layouts.json`, layout flagged `enabled: false` | Logged as `skipped`. Not an error. |

No silent failures. Every code path that doesn't produce a PDF must produce a log line the colleague can see in the phase summary.

## Auth

Visualizer CLI requires `/username` and `/password`. Spec leaves the storage mechanism open for the implementer to pick based on the corporate setup:

- **Recommended default:** `.env` next to the driver (matches how other Westland scripts handle creds; gitignored). Format: `P6_USERNAME=...`, `P6_PASSWORD=...`, `P6_ALIAS=PMDB`.
- **Alternative:** Windows Credential Manager via `keyring` Python package.
- **Alternative:** prompt once per session, cache in memory only.

Whichever is chosen, the password must not appear in the actions.xml file (which would get logged) and must not be logged via Visualizer's `/logfile` parameter. The Visualizer CLI accepts credentials only via command-line flags, not via the actions.xml — that's why the `/password=` flag exists separately.

Oracle support note [2102181_1](https://support.oracle.com/knowledge/More%20Applications%20and%20Technologies/2102181_1.html) covers a credentials-prompt workaround if needed; paywalled, but referenced here so the implementer knows where to look.

## Testing strategy

The full integration test requires P6 Pro + Visualizer + a shared corp database — not feasible in CI. Test in three layers:

### Layer 1: Pure-function unit tests (CI)

`render_filename`, `actions.xml` builder, Visualizer log parser, registry loader/validator. No subprocesses, no filesystem outside `tempdir`. Lives in `scheduling/skills/schedule-update/tests/test_print_layouts.py`.

Covers:
- Template substitution including `{revision}` auto-increment
- Malformed `layouts.json` raises `RegistryError` with a useful message
- Log parser identifies per-layout success/failure across the formats Visualizer emits
- `actions.xml` builder produces valid XML against a known-good golden file

### Layer 2: Mocked-subprocess tests (CI)

Same test file, but with `subprocess.run` mocked to return fixture Visualizer outputs (one batch-success, one batch-mixed, one batch-failure-then-retry-succeeds, one global-failure). Verifies the driver's orchestration logic without needing Visualizer installed.

### Layer 3: Live integration smoke test (manual, gated)

A `scripts/print_layouts_smoke.py` that runs against a real project with a 1-entry `layouts.json` pointing at a known-stable `.plf`. Run manually before merging changes that touch `print_layouts.py`. Document in the skill's README so any future implementer knows it exists.

CI does not run Layer 3. There's no value in trying to mock Visualizer at that level.

## Implementation order (suggested)

1. Component 3 (`xps_to_pdf.py`) first — smallest, most isolated, can be smoke-tested with any XPS file. Verify the Microsoft Print to PDF approach actually works on the target Windows build before committing more code.
2. Component 1 (registry schema + loader/validator) — pure code, fully unit-testable.
3. Component 4 (filename rendering) — pure function.
4. Component 2 (`print_layouts.py` driver) — orchestrates the above plus the Visualizer subprocess. Build with mocked subprocess first, then live-test.
5. Component 5 (phase markdown) — last, once the driver is solid.
6. Wire into the schedule-update skill: add the phase to the `report` flow's phase list. No changes to `email_draft_io.py` or `phases/procore.md` needed if the PDF naming follows the existing convention.

Bump scheduling plugin version. Open PR. Standard release flow per [CLAUDE.md](../../../scheduling/CLAUDE.md).

## Open questions for the implementer

These are decisions left intentionally for the implementer because they depend on details that aren't visible from this spec session:

1. **Microsoft Print to PDF output path setting.** The PowerShell `PrintTo` invocation doesn't take a destination path directly. The implementer needs to verify the registry-hack approach works on the actual target Windows build, or pick a different XPS→PDF tool if not.
2. **Visualizer install path.** Standard install location vs. configured per-machine env var. Driver should accept `visualizer_exe` arg with sensible default discovery.
3. **Alias / database name.** Whatever Westland's corporate Visualizer setup uses. Hardcode in `.env`, not in code.
4. **Initial `layouts.json` content per project.** Probably 6–10 starter entries — Camron to enumerate during initial rollout. Could be scaffolded by the project-init skill.
5. **Whether to print one combined PDF per project or one PDF per layout.** Spec assumes per-layout. If a combined-deliverable form is needed (one big PDF per project for the owner), add a `combine: true` field to the registry and `pypdf`-merge at the end. Out of v1 scope unless requested.

## Future work (v2+)

- **Project-init scaffolding for `layouts.json`.** When `schedule-project-init` creates a new project's schedule folder, prompt for a starter layout set or copy one from a similar project.
- **One combined PDF per project** (see open question 5).
- **Layout diff report.** Detect when a `.plf` referenced in the registry has changed since the last weekly run (file mtime / hash). Useful for traceability.
- **GanttReport + TSLDReport.** v1 covers Gantt only. Time-Scaled Logic Diagrams have the same CLI shape; small extension to the registry adds a `report_type: "tsld" | "gantt"` field.

## Alternatives considered

### JS Gantt renderer (XER → HTML+SVG → Playwright → PDF)

We have ~70% of the infrastructure already (XER parsing, CPM engine, Playwright HTML→PDF pipeline at `schedule-update/references/html-to-pdf.js`, SVG-in-HTML chart pattern from `references/charts/`). Building the Gantt renderer itself is a ~40–80 hour project, and the unbounded tail is "make it look exactly like P6" — page tiling for wide schedules, relationship arrow routing, bar joining across summaries, text truncation, etc. P6 has 25 years of accumulated rendering decisions that are hard to match pixel-for-pixel.

**Rejected for v1 because:** the prints go to owners, and pixel parity matters. The Visualizer pipeline gives that for free. The JS-renderer approach is the better long-term play — Oracle-free, git-diffable configs, integrates with the XER-table effort — but it's a meaningful build with a real risk of "looks great, but a P6 power-user can tell." Worth revisiting in v2+ when the Visualizer approach has been used long enough to know what its real limitations are.

### P6 Pro UI automation (AutoHotkey / pywinauto)

Drive P6 Pro itself: open project, apply layout, File → Print → Microsoft Print to PDF, save. Covers all layout types because it's literally what the colleague clicks today.

**Rejected because:** UI automation is brittle. Any P6 patch that moves a menu, any screen-resolution change, any modal dialog interruption breaks the script. Maintenance tax compounds. The Visualizer CLI is a stable contract; the P6 Pro UI is not.
